## 从定时器由 TIM2(CH1/PA0) 改为 TIM3(CH2/PA7)

用户自己在 CubeMX 里把从定时器的 PWM 引脚从 TIM2_CH1(PA0) 改到了 TIM3_CH2(PA7)，
并重新生成了 `tim.c` / `tim.h`（已含 `htim3`、`TIM_CHANNEL_2`、PA7 的 MspPostInit）。
但 `main.c` 与 `MX_PWM_Start_PhaseLocked()` 仍在用 `htim2`，属于编译不过的状态。

### 改动清单
- `Core/Inc/tim.h`
  - 宏重命名：`PWM_PULSE2` -> `PWM_PULSE_T3`，`TIM2_CNT_PRESET` -> `TIM3_CNT_PRESET`
  - 调试变量 extern：`g_dbg_tim2_*` -> `g_dbg_tim3_*`
  - 注释中 PA0/CH1 -> PA7/CH2
- `Core/Src/tim.c`
  - `MX_PWM_Start_PhaseLocked()`：`htim2`->`htim3`、`TIM_CHANNEL_1`->`TIM_CHANNEL_2`、
    `TIM2->CNT` -> `TIM3->CNT`
  - 调试快照变量改名
- `Core/Src/main.c`
  - `__HAL_TIM_SET_COMPARE(&htim3, TIM_CHANNEL_2, PWM_PULSE_T3)`
  - while 循环快照改为 TIM3；顺手把过时的注释 "恒等于 684" 更正为 3595
- `PWMVerify.ioc`
  - `ProjectManager.functionlistsort` 里遗留的 `MX_TIM2_Init` 改为 `MX_TIM3_Init`

### 关键结论：触发源仍是 ITR0，不用改
F103 的 TIMx 内部触发映射（RM0008）：
```
从机   ITR0    ITR1    ITR2    ITR3
TIM1   TIM5    TIM2    TIM3    TIM4
TIM2   TIM1    TIM8    TIM3    TIM4
TIM3   TIM1    TIM2    TIM5    TIM4
TIM4   TIM1    TIM2    TIM3    TIM5
```
**TIM3 的 ITR0 同样是 TIM1**，所以 `TIM_TS_ITR0` 原样保留即可。
（网上博客的 `GetInternalTrigger()` 宏表可佐证：TIM3+TIM1 -> TIM_TS_ITR0。）

### 其余不变
- TIM3 也在 APB1，定时器时钟同样 2×PCLK1 = 72 MHz => ARR=3599/20kHz、PSC=0 全部沿用。
- 时基、死区内缩推导、预置 CNT=3595、启动顺序（先 TIM3 后 TIM1）逻辑完全不变。
- 输出变为：PA8(TIM1) 高 [0,1800)，PA7(TIM3) 高 [5,1795)，内缩关系一致。

### 验证
arm-none-eabi-gcc (STM32CubeCLT 1.22.0) `-c -Wall -Wextra` 编译
main.c/tim.c/gpio.c/stm32f1xx_hal_msp.c/stm32f1xx_it.c 全部 exit 0、零警告。

### 🔴 坑1：CubeMX 重新生成会把 HSE 模式改回去（本次事故）
用户这次"改 TIM2→TIM3 引脚"重新生成后，`SystemClock_Config()` 又从
`RCC_HSE_ON` 变回 `RCC_HSE_BYPASS`（ioc 里 `PD0-OSC_IN.Mode=HSE-External-Clock-Source`）。
后果与 2026-10-10 记录的完全一致：
`RCC_CR=0x00055B83`（HSEON=1/HSEBYP=1/**HSERDY=0**）→ `HAL_RCC_OscConfig()` 超时 →
`Error_Handler()`（PC=0x0800116E）→ **TIM1/TIM3 寄存器全 0，没有任何 PWM**。
**正确做法：ioc 里 HSE 选 `HSE-External-Oscillator`（晶振），生成出来才是 `RCC_HSE_ON`。**
用户本次已自己改对，验证通过（`RCC_CR=0x03035B83`）。

### 🔴 坑2：F1 的 DBGMCU_CR 位映射（与 F4 完全不同，别再记错）
`stm32f103xb.h` 实测定义（`DBGMCU_CR` @ `0xE0042004`）：
```
bit0 SLEEP  bit1 STOP  bit2 STANDBY
bit5 TRACE_IOEN   bit6:7 TRACE_MODE      <-- 不是 TIM 停止位！
bit8 IWDG_STOP  bit9 WWDG_STOP
bit10 TIM1_STOP  bit11 TIM2_STOP  bit12 TIM3_STOP  bit13 TIM4_STOP
bit14 CAN1_STOP  bit15 I2C1_SMBUS  bit16 I2C2_SMBUS
```
（我最初按 F4 印象写了 bit5/bit7 → 实际设的是 TRACE_IOEN/TRACE_MODE，TIM1 根本没冻结。）
另：**J-Link 每次连接会自动把 DBGMCU_CR 写成 `0x307`**（SLEEP/STOP/STANDBY/IWDG/WWDG），
手动清零后下次连接又被改回来——这是 J-Link 的正常行为，不影响运行。

### ✅ 无示波器的相位实测法（可复用）
DBGMCU 冻结 + 单次 halt 内原子读两个 CNT：
```
si SWD
speed 4000
connect
w4 0xE0042004, 0x00001400     ; bit10 TIM1_STOP | bit12 TIM3_STOP
halt
mem32 0x40012C24, 1           ; TIM1->CNT
mem32 0x40000424, 1           ; TIM3->CNT
mem32 0x40012C24, 1           ; 复读校验"真的冻结了"
mem32 0x40000424, 1
w4 0xE0042004, 0x00000000
g
exit
```
冻结后两路计数器静止，同一次 halt 内读到的 `CNT` 差值 = 真实相位差（否则 SWD 读延迟
会淹没 5~6 count 的差异）。**必须复读校验**：若同一寄存器两次读数不同 → 没冻结，数据无效。

### 实测结论（4 次独立测量，计数器值各异，结果一致）
- TIM1 `CNT` - TIM3 `CNT` = **6 counts**（设计值 `PWM_DEADTIME_CNT` = 5）
- 即主→从触发链路有**固有 1 个计数（13.9ns）延迟**，与预置 CNT 的 5 叠加成 6
- 后果：内缩**不对称** —— 上升沿滞后 6 cnt(83.3ns)、下降沿提前 4 cnt(55.6ns)
  （原设计意图是 5/5 对称）；**脉冲宽度仍是 1790 cnt，与设计一致**
- 若要与设计对齐：`TIM3_CNT_PRESET` 由 `(ARR+1)-N` 改成 `(ARR+1)-N+1` 即可补偿（待用户裁决）

### 寄存器判据（全部命中）
| 项 | 读数 |
|---|---|
| RCC_CR / CFGR | `0x03035B83`(HSERDY=1,PLLRDY=1) / `0x001D040A`(SW=SWS=PLL, PLLSRC=HSE, ×9 → 72MHz) |
| TIM1 | CR1=1(CEN), CR2=0x20(MMS=010 TRGO=更新), SMCR=0, CCER=1, ARR=3599, CCR1=1800, BDTR=0xA000(MOE=1) |

| PC | `0x08001510`（主循环，不再是 Error_Handler） |

## ★ 攻克：让 AI 独立驱动 Saleae Logic 2 采集（三层坑，全部定位）

用户要求"独立拉取逻辑分析仪数据、不靠人工点 GUI"。逐层排查后打通，全自动链路已固化。

### 坑1（根因）：WorkBuddy 注入的 `ELECTRON_RUN_AS_NODE=1`
宿主 shell 的环境里有：
```
ELECTRON_RUN_AS_NODE=1
NODE_OPTIONS=--require="D:/WorkBuddy/.../node-language-shim.cjs"
BASH_ENV=...shell-runtime-bash-env.sh
```
Logic.exe 是 **Electron 应用**，而 `ELECTRON_RUN_AS_NODE=1` 会让 Electron **退化成纯 Node**：
GUI 完全不启动、脚本跑完即退，且**不留任何日志目录**（看起来像"秒退/根本没跑"）。
**铁证**：`Logic.exe --help` 打印的是 **Node.js 的 usage**，不是 Electron 的；
且带未知参数时 Node 报 `D:\logic\Logic.exe: bad option: --automation`（rc=9）。
→ 解决：启动前 `env -u ELECTRON_RUN_AS_NODE -u NODE_OPTIONS -u BASH_ENV`。

### 坑2：GPU 进程 access violation
清掉坑1后 Electron 真起来了，但立刻：
```
ERROR:gpu_process_host.cc:996] GPU process exited unexpectedly: exit_code=-1073741819
FATAL:gpu_data_manager_impl_private.cc:417] GPU process isn't usable. Goodbye.
```
（-1073741819 = 0xC0000005 访问违例）`--disable-gpu` **无效**。
→ 解决：用 **`--in-process-gpu`**（GPU 放主进程，不再单独起 GPU 进程）；
   或 `--no-sandbox --disable-gpu`（实测两者都能起来）。

### 坑3：Automation Server 默认关闭
端口 10430 不开。在 `resources/app.asar` 里挖到配置键名与默认值：
`automationServerEnabled` / `automationServerPort`(=10430) / `automationHost`(=127.0.0.1)，
由 `dataStore.get('automationServerEnabled', false)` 读取，dataStore 就是
`%APPDATA%\Logic\config.json`（`automaticallyStartCaptureMSO`、`theme` 等都在同一文件）。
→ 解决：在 config.json 顶层加 `"automationServerEnabled": true`（已备份为 `config.json.clbak`）。
   **注意**：应用包里还有 `--automation` 命令行开关，但那个参数是在 Electron 模式下才有效；
   坑1 存在时会被 Node 拒掉，别被误导。

### 坑4：导出目录必须用**绝对路径**
`capture.export_raw_data_csv(directory=<相对路径>)` 会被 Logic 按**它自己的 cwd**（`D:\logic`）解析，
CSV 静默落到 `D:\logic\.cl\capture\saleae\digital.csv`，脚本却报"导出失败（未生成）"。
→ 解决：传绝对路径。（已清理该杂散目录）

### 固化产物（项目内，可复用）
- `.cl/tools/logic_launch.sh` —— 独立拉起 Logic 2 + 等端口（幂等：端口已开则直接返回）
- `.cl/tools/saleae_capture.sh` —— **一条命令**：启动 → 采全部 8 通道 → 自动识别翻转通道 → 解析相位
- `.cl/tools/pwm_phase_check.py` —— 修了两个 bug：①表头 `Time [s]` 不被 `sniff_time_unit()` 识别，
  落到启发式把"秒"当"微秒"（周期/频率差 1e6 倍）；②通道标签写死 `从(PA0)` → 改用表头名；
  ③新增"下降沿超前量 + 内缩对称性"判定。
- 依赖：`logic2-automation` 装在 `C:\Users\admin\.workbuddy-ai\binaries\python\envs\saleae`

### ★ 逻辑分析仪实测结果（两次采集一致，与 SWD 法互证）
探头实际接在 **CH5 / CH7**（不是 CH0/CH1）——CH0~CH4、CH6 悬空恒为高。
```
主(CH5=PA8/TIM1): 频率=20.000 kHz  周期=50.000 us  占空比=50.00%
从(CH7=PA7/TIM3): 频率=20.000 kHz  周期=50.000 us  占空比=49.75%
上升沿滞后: 中位=83 ns  -> N_rise = 5.98 counts   (SWD 法: 6 counts)
下降沿超前: 中位=42 ns  -> N_fall = 3.02 counts
内缩对称性: 5.98 vs 3.02 -> 不对称（差 ~3 cnt）
```
**结论**：20kHz、PA8 50.00%、PA7 49.75%（设计 1790/3600=49.72%，吻合）；
上升沿滞后两种独立方法一致 = **6 counts**（设计 5），
即主→从触发链路固有 1 count 延迟 → 内缩不对称（设计意图是 5/5 对称）。
采样率上限 24 MSa/s（41.67ns/样本），所以 1 count(13.89ns) 的量化误差约 ±1.5 count，
下降沿那 3.02 与理论 4 的差落在量化误差内。
